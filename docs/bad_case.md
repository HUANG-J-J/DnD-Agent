# Bad Case 记录

格式：输入 → 预期 → 实际 → 原因 → 状态。原因要追到具体代码和机制，不写"模型太笨"。

---

## 1. 背景加值失败，角色照样建出来，模型不知道

- 输入：半精灵 / 血猎手 / 士兵，选"② 只用半精灵种族加值，背景不加属性"，确认创建
- 预期：加值不合法时**不建角色**，把错误回传给模型，模型去问玩家怎么改
- 实际：模型传了 `bonus_distribution="A"`、`bonus_stat1="CHA"` 当"占位"。终端打出 `成功创建角色：亚瑟 (错误：CHA 不在你的背景可选范围内！)`，角色照样建了。模型收到的 tool 消息只有"创建成功，最终属性……"
- 原因：
  1. `apply_background_bonus` 失败时 **return 一个错误字符串**而不是抛异常，调用方也不检查返回值，所以加值失败后流程照常往下走
  2. `bonus_msg` 只 `print` 到终端，**没有拼进回传给模型的字符串**
  3. schema 里 `bonus_distribution` 是必填且只能填 A / B，没有"不加值"的选项，模型只能硬塞一个占位值
- 状态：已修（发现 11-09，修复 11-24）
  - 三处 `return "错误..."` 改为 `raise ValueError`，错误信息列出背景可选属性；非法的 distribution（如 "C"）也抛错，以前会悄悄返回 `None`
  - `bonus_stat1` 不再必填，`stat1`/`stat2` 默认 `None`，方案 B 不用再塞占位值
  - 工具回传给模型的字符串带上加值结果
  - `tool_create_character` 最后才 `state.hero = hero`，加值失败时这局不会留下建了一半的角色
- 验证：`tests/test_character.py`。原先标为 `xfail(strict=True)` 的测试在修复后变成 XPASS，CI 变红提醒删除标记；新增"加值失败后 `state.hero is None`"测试

## 2. 模型用"DM 裁定"推翻代码的状态

- 输入：接第 1 条，玩家约定"保留半精灵种族加值"，确认创建
- 预期：以代码算出的角色卡为准；规则冲突时模型提示玩家，不自行改数值
- 实际：建卡后模型说"工具回传的是未加成的原始值"，在叙事里自己改成敏捷 15→16、体质 14→15、魅力 12→14、HP 10→12、AC 12→13。此后状态栏每轮注入的仍是代码里的值，两边长期不一致
- 原因：
  1. 模型和玩家约定了种族加值，但 **schema 没有种族加值字段，也没有任何能修改属性的工具**，这套规则在代码里表达不出来，模型只能在叙事里自己改
  2. system prompt 没有声明"【当前真实状态】是唯一权威，DM 不得自行修改数值"
- 状态：未修（发现 11-09）。修法方向：用 `enum` 限死物种 / 职业 / 背景，只允许代码支持的规则；prompt 写明状态栏权威

## 3. 未知职业静默降级

- 输入：职业选"血猎手"（第三方职业，不在 `CLASS_HIT_DICE` 里）
- 预期：代码拒绝建卡并提示"不支持的职业"，或至少报错
- 实际：角色正常建出，HP = 10（d8 + 体质 2），终端没有任何提示。模型认为血猎手是 d10，应为 12
- 原因：
  1. `CLASS_HIT_DICE.get(self.job, 8)` 的默认值 `8` 把"职业不存在"这个错误**悄悄吞掉**，用一个看似合理的值继续跑，属于静默降级
  2. schema 里 `job` 是自由字符串，没有限制取值范围
- 状态：已修（发现 11-09，修复 11-22，commits `0d7041d`、`232f5af`）
  - schema 里 `job`、`background` 加 `enum`，取值直接来自 `CLASS_HIT_DICE` / `BACKGROUND_STATS` 的 key，规则表是唯一数据源
  - `Character.__init__` 开头校验，非法值 `raise ValueError`，错误信息列出全部合法选项；去掉 `.get(job, 8)` 和背景的同类默认值
  - 两道防线：enum 让模型尽量不传错，代码校验保证传错了也建不出角色
- 验证：
  - 正常情况下模型看到 enum，直接拒绝血猎手，不调用工具
  - 故障注入：临时删掉 `job` 的 enum，模型传入"血猎手" → `ValueError` 经工具 `try/except` 回传 → 模型如实说明、列出 12 个合法职业、让玩家重新选，没有替玩家决定

## 4. 模型编造代码的出错原因

- 输入：接第 2、3 条，问"我现在血量多少？"
- 预期：模型以状态栏为准；对不上时如实说不一致，不猜测原因
- 实际：模型说"系统状态栏写的 10/10 是没有把体质加值算进去的结果"。实际代码算了体质加值，错在生命骰（见第 3 条）
- 原因：模型看不到代码，只看到结果数字。数字和它的认知对不上时，它会**编一个听起来合理的解释**，而不是承认不知道
- 状态：未修（发现 11-09）。修法方向：工具结果里写出推导过程，例如"HP 10 = d8（默认）+ 体质 2"，模型不用猜；同时修掉第 2、3 条，从源头消除不一致

## 5. API 中途失败，程序崩溃，历史被弄坏

- 输入：把 while 循环里那次 `call_llm` 的模型名故意改错，发一句建卡
- 预期：`except` 接住错误，打印"调用失败"，历史回到这一轮开始前，下一句能正常对话
- 实际：程序直接崩溃，报 `tenacity.RetryError`。即便接住了，`messages.pop()` 只删掉最后一条 tool 消息，留下一条没有结果的 `assistant(tool_calls)`，之后每次请求都会 400
- 原因：
  1. `@retry` 重试耗尽后抛的是 `RetryError`，**不是 `openai.APIError` 的子类**，`except` 接不住
  2. 400 这种永久错误也被重试了 3 次，白等几秒
  3. `pop()` 只在第一次请求就失败时是对的（那时最后一条是 user 消息）；循环内失败时，一轮里已经 append 了 assistant 和 tool 消息，只删一条会破坏调用链
- 状态：已修（发现 11-09，修复 11-20，commit `17ad0b8`）
  - `@retry` 加 `reraise=True`，并用 `retry_if_exception_type` 只重试超时、断网、429、5xx；client 设 `max_retries=0`、`timeout=30`，避免两层重试叠加
  - 每轮开始前记 `turn_start = len(messages)` 和 `hero_before`，失败时 `del messages[turn_start:]` 并回滚 `my_hero`，一轮要么全成功、要么什么都不留

## 6. DM 向玩家暴露实现细节

- 输入：建卡时坚持要当"血猎手"（schema 已有 enum）
- 预期：DM 用游戏内的说法拒绝，例如"这片大陆上没有血猎手的传承"，再给出替代方案
- 实际：DM 对玩家说"create_character 工具的职业栏是写死的 12 个选项""这条流水线物理上跑不通"。拒绝本身是对的，但说法很出戏
- 原因：
  1. system prompt 没有说明"工具和系统状态是给 DM 用的，玩家看不到"，模型把自己的约束原样转述给了玩家
  2. 模型需要解释"为什么不行"，而它知道的真实理由就是工具限制，没有被引导去换成世界观内的理由
- 状态：未修（发现 11-22）。修法方向：prompt 写明不得向玩家提及工具名、参数、系统；拒绝时用世界观内的理由，或用"本团规则不支持"这类桌面用语。改完用同一输入复测，对比前后
